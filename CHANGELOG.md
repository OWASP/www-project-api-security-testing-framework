# Changelog

Releases before 2.0.2 are described on the [GitHub Releases page](https://github.com/OWASP/www-project-api-security-testing-framework/releases).

## 2.1.0 (unreleased)

Several checks claimed to be unauthenticated or to use one identity while sending the scan's credentials, and credentials could follow a redirect to another host. This release sends the stricter request first (no credentials, the secondary token alone, only the target host). When that request is rejected, the check falls back to the request 2.0.2 sent, so it still finds what 2.0.2 found. A result that cannot be shown to be unauthenticated or attributable to one identity is reported at a lower severity, and its title and evidence say what was sent.

### Fixed

- **Checks no longer disappear on look-alike paths.** Auth and 2FA endpoints were recognized by substring, so `/api/tokens`, `/api/authors`, `/api/authorities`, `/api/discount-codes` and `/api/otpauth-free-paths` were taken for login or OTP endpoints and never got the missing-auth and JWT checks. Paths are now also split into words (on `-`, `_`, `.`, camelCase and acronym runs, case-insensitively, ignoring path parameters and the query string) and matched by stems (`login`, `logon`, `signin`, `authenticat`, `oauth`, `saml`, `jwt`, `session`, and others) and whole-word keywords (`auth`, `token`, `otp`, `mfa`, and others). The 2.0.2 substring classification is still computed alongside and nothing is taken away: a path gets the login checks if either classification calls it a login path, the 2FA checks if either calls it a 2FA path, and the missing-auth and JWT checks unless both do. Where the two disagree (`/api/tokens`, `/api/logon`, `/api/jwt`, and others) the path now gets both kinds of check. The NoSQL check uses the same rule for "login-like". Ambiguous paths receive more requests.
- **OpenAPI root-level security.** Discovery only read an operation's own `security`, so a spec with root-level security made every endpoint look public. The effective requirement is the operation's `security` (an explicit `[]` means public), else the root `security`, else public: `securitySchemes` alone require nothing, as in the OpenAPI specification. Swagger 2.0 specs are unchanged.
- **Credentials stay on the target.** A redirect to another host carried the API-key header, custom headers and cookies with it, and discovery fetched a spec URL named by a Swagger UI page with the scan's credentials even when it was on another host. A request to any host:port other than the target is still made, but without `Authorization`, the API-key header, cookies, `Proxy-Authorization` (kept only on a plain-http request through an HTTP proxy) and every configured custom header except `Accept`, `Accept-Encoding`, `Accept-Language`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `User-Agent`, `Host` and `Connection`. A warning is logged once per host:port. `http://host` redirecting to `https://host` on the target's own host (port 80 to 443) counts as the target; other port changes do not. A redirect from https to plain http never carries credentials, even to a host listed in the new `scopeHosts` config key (`host` or `host:port`), which lists extra hosts that may receive them. On a redirect chain through a listed host and back to the target, `Authorization` is restored on every in-scope hop. `followRedirects` now takes effect (default `true`).
- **Unauthenticated means unauthenticated.** The BFLA admin-path and HTTP-method probes, the debug, shadow-endpoint, documentation and GraphQL IDE probes, the missing-authentication check, the brute-force lockout and user-enumeration checks and the NoSQL bypass probes on login-like paths reported "without authorization", "publicly accessible" or anonymous-attacker results from requests that carried the token, API key, custom headers and cookies. They now send the request with no credentials and no custom header except the protocol headers above (identity often travels in headers such as `X-User-Id`). If that request is not accepted, the request 2.0.2 sent is sent too, and a result is reported as "(reachable with the configured credentials)", "(reachable with the configured headers)" or "(reachable with cookies set during the scan)" at a lower severity (an admin path drops from CRITICAL to MEDIUM, a NoSQL authentication bypass from CRITICAL to HIGH). The missing-authentication check, when rejected without any custom header, is also sent with no `Authorization`, API key or cookie but with the custom headers kept (the 2.0.2 request) and, if accepted, reported with the kept header names in its evidence. The GraphQL guessed-cookie comparison is sent without credentials when the baseline it compares with was anonymous.
- **Cross-user BOLA behind API gateways.** The secondary identity's request now carries only `--secondary-token`, with no primary API key, custom headers or cookies. A gateway that also requires an application key rejected that request, so the secondary token is then sent plus the application credential (the `--api-key` and any custom header whose name looks like an application or gateway key), with a control request sending that credential alone to grade the result: CRITICAL, HIGH if the control could not be sent, or MEDIUM if the application credential alone reaches the object. If both are rejected, the request 2.0.2 sent (the primary request with only `Authorization` replaced) is sent and, if accepted, reported as "Broken Object Level Authorization (Cross-User Access, other configured headers kept)" at HIGH, listing the headers that rode along. A plain bearer API is tested as before and no API key is sent.
- **Login walls are not exposed endpoints.** The debug and BFLA admin probes were sent without credentials but screened against an unknown-path baseline fetched with credentials, so behind a login wall every probed path was reported. An anonymous probe is now compared with an unknown-path baseline that is also fetched without credentials.
- **Lockout check behind a gateway.** When every attempt got the same 401/403 as a path that does not exist, the attempts may not have reached the login handler, yet "No Account Lockout" was reported at MEDIUM. The attempts are now repeated with the configured credentials when there are any, and a result that still cannot be told apart from a pre-handler rejection is reported at LOW as "No Account Lockout or Rate Limiting on Repeated Failed Logins (not confirmed)", saying so. It is never dropped.
- **mTLS comparison on APIs that also need a token.** The certificate-only pair is sent first, as before. If the valid certificate alone is rejected and the scan has credentials, both certificates are sent again with the same configured credentials, over a connection that validates the server's certificate and host name (a token is never sent over an unvalidated connection). If the server's certificate is not trusted by this JVM, no credential is sent and an INFO finding "mTLS Certificate Comparison With Credentials Not Made (server certificate not trusted)" says so.

- **SQL injection false CRITICAL.** A database error in the response was reported as CRITICAL SQL injection even when the payload had not caused it. On VAmPI, another check resets the tables mid-scan, and a register request that landed during the reset got "sqlalchemy.exc ... no such table: users"; the finding did not reproduce by hand. Before reporting, the check now sends an ordinary value in the same field or path segment and then the payload again. It is CRITICAL only if the payload reproduces the error and the ordinary value does not; otherwise it is reported as MEDIUM "Possible SQL Injection (not reproducible)", or INFO "SQL Injection Check Inconclusive" when the ordinary value errors too. If the re-check request fails, the CRITICAL finding is kept. A database error that describes the target's own state (a missing or recreated table, a locked database, a duplicate record) and has no syntax error in it is reported as INFO "SQL Injection Check Inconclusive" without a re-check, because a re-check taken while the target is resetting its tables can fail the same way. An unconfirmed result no longer stops the behavioural and NoSQL checks from running.
- **Weak default credentials found in an account the scan created.** The ReDoS and SQL/NoSQL checks filled the fields they were not testing with `"test"`, so a register endpoint created a real `test`/`test` account, and the broken-authentication check then logged in with it and reported CRITICAL "Weak Default Credentials Accepted". Those fields are now filled with `astf-filler`.
- **BOLA checks no longer modify or delete other users' objects by default, and find stateful BOLA** (D1, D6, D7 in the ASTF gap analysis). On `PUT`/`PATCH`/`DELETE`/`POST` endpoints the cross-user check and ID substitution sent the real method, including `DELETE` to guessed IDs `1`, `2`, `100`, `999` and `0`. The primary identity's request also went first, so on a stateful API the secondary identity found nothing left and the bug was missed. Write endpoints are now probed with a read-only `GET` on the same URL unless the new `--allow-destructive` flag (config `allowDestructive`) is set; a check that cannot run read-only is reported as INFO "Check Held Back" instead of disappearing. With the flag, the secondary identity's request is sent first. Cross-user access is CRITICAL only when the secondary identity receives the primary identity's object and an anonymous request does not; a 2xx with different content is MEDIUM "Not Confirmed". `PATCH` endpoints were sent as `GET`; they are now sent as `PATCH`.
- **Open redirect detection never saw 3xx responses** (#173, #183). The default HTTP client followed redirects before `testOpenRedirect` could inspect them, so a 302 to an attacker `Location` produced zero findings. Open-redirect probes now use a dedicated non-following client; detection requires a `Location` that sends the browser to the injected external host: an absolute URL, or a scheme-relative one (`//host`, `/\host`, `\\host`) that browsers resolve to another host. Relative paths and same-host redirects are ignored.
- **Debug and API-docs probes skipped without `/`** (#174, #184). Security Misconfiguration (API8) debug/actuator probes and Improper Inventory Management (API9) documentation/shadow-doc probes used to run only when the endpoint list contained `/`. Grey-box scans with `--endpoints-file ... --no-discovery` usually omit `/`, so those probes never ran. They now run once per scan target (base URL), on the first endpoint seen for that base, with the same soft-404 / SPA-fallback screening as before.
- **API6 false HIGH on validation-only bursts.** (#175, #185) `UnrestrictedAccessToSensitiveFlowsTestCase` treated HTTP 422 as a successful abuse attempt, so an endpoint that rejected every request as invalid was reported HIGH for missing rate limiting. Only accepted (2xx) attempts count toward the HIGH finding. A burst that was never throttled but had rejected attempts is MEDIUM "Not Throttled" when some attempts were accepted or a sample `requestBody` was configured (rejected attempts can be failed OTP or coupon guesses), and INFO "Inconclusive" when ASTF could only send `{}`. 404, 405 and 410 are not counted as attempts. Body-level throttle markers (`rate limit exceeded` / `throttled` / …) and HTTP 423 are recognized the same way as in the API4 rate-limit check.
- **Server-side template injection detection was unreachable** (#179, #186). The probe used `{{7*7}}`/`${7*7}` and looked for `49`, but the success-pattern loop explicitly skipped `49` to avoid false positives, so SSTI could never fire. Probes now use the unique marker `1337*1337=1787569` across common template syntaxes, require the marker to be absent from the baseline, ignore pure expression echoes, and name the engine family in evidence.
- **Mass-assignment probes dropped required fields.** (#176, #187) `BrokenObjectPropertyLevelAuthorizationTestCase` sent only privileged keys (`isAdmin`, `role`, ...), so register-style endpoints that require `username`/`password` returned 400 before property binding ran (the documented VAmPI `POST /users/v1/register` miss). Privileged fields are now merged into the discovered request body, or, for a `POST` with no known body, into a unique `astf-*` filler body; a `PUT` or `PATCH` with no known body keeps sending the privileged keys alone, because a filler that is accepted would overwrite the existing object. `credit` is included among the probed keys.
- **Security header policy (API8)** (#180, #188). `X-XSS-Protection` is no longer treated as a required header (OWASP marks it deprecated); a LOW finding is raised only when it is present with a value other than `0`. Authenticated responses are now checked for `Cache-Control: no-store` (LOW when absent; `no-cache` alone is not enough). A response counts as authenticated when it sets a cookie, or when it is a `2xx` to a credentialed request and the same URL without credentials gets `401`/`403`; public endpoints are not flagged.
- **SSRF body probes replaced the whole request body.** (#181, #189) `ServerSideRequestForgeryTestCase` sent only `{"url":"<payload>"}` (and other single-field variants), so endpoints that validate required fields rejected the probe before any fetch. When a discovered JSON body exists, every field is kept and the payload is substituted into URL-shaped fields (by name or http(s) value). Whether or not the body has one, each historical parameter name (`url`, `webhook`, `callback`, …) is also tried alongside the existing fields, so the parameter coverage is unchanged, and field names are matched by whole word (`feed_url` yes, `security_level` no); endpoints with no body still get the historical single-field probe. GCP/Azure "missing metadata header" responses are now HIGH evidence that the metadata service was reached, still subject to the 2.0.2 payload-echo and baseline filters.

### Added

- **Custom OpenAPI specification** (#167). `--openapi <url-or-file>` (config key `openApiSpec`) takes the endpoints from a specification you name instead of searching the target for one: an `http(s)` URL, or a local JSON or YAML file. It is read even with `--no-discovery`. If it cannot be read, or is not an OpenAPI or Swagger document, a warning says why and automatic discovery runs instead (unless discovery is disabled), so a typo never leaves the target untested. A URL on another host is fetched without credentials unless the host is in `scopeHosts`; a URL on the target gets them. `--endpoints-file` still takes precedence.
- **GraphQL query-field brute-force detection** (#117). The existing brute-force check only matched a *mutation* named like a login. An authentication gate exposed as a *query* field and not named like a login: DVGA's `systemDiagnostics(username, password, cmd)`: went undetected. A new check introspects query fields for one governed by both a username-like and a password-like argument, sends eight failed attempts, and reports a missing-rate-limiting finding (MEDIUM) if no 429/423 lockout appears. The call carries a selection set only for object-returning fields, so a scalar-returning field like `systemDiagnostics: String` is queried correctly. Discovery relies on introspection being enabled. Live-verified against DVGA: reported "No Rate Limiting on GraphQL Query-Field Authentication" for `systemDiagnostics`.
- **CORS allowlist bypasses** (#204). The CORS check only sent `https://evil-attacker.com`, so an allowlist that trusts `Origin: null` or matches by prefix or suffix was never reported. When that first origin is neither wildcarded nor reflected, three more origins are tried: `null`, the target host as a prefix of an attacker domain (`https://api.example.com.evil-attacker.com`) and an attacker domain ending in the target's last two labels (`https://evilexample.com`, not sent for IP addresses or single-label hosts). Only an exact echo in `Access-Control-Allow-Origin` counts. "CORS Origin Allowlist Bypass" is HIGH with `Access-Control-Allow-Credentials: true` and MEDIUM without; "CORS Policy Trusts the null Origin" is HIGH with credentials and LOW without.
- **Access control bypass on protected admin paths** (#206). An admin path that answered `401`/`403` without credentials was treated as protected. The same anonymous `GET` is now also sent as `//admin`, `/admin/`, `/admin;/`, `/admin..;/`, `/%61dmin`, `/ADMIN` and `/admin%20`, and to `/` with `X-Original-URL` and `X-Rewrite-URL` naming the path. A `2xx` API response that is not the target's unknown-path answer is reported as CRITICAL "Administrative Endpoint Access Control Bypass"; for the header forms the body must also differ from a plain anonymous `GET /`. Dot-segment forms (`/./admin`, `/%2e/admin`) are not sent because OkHttp normalises them. Each admin path is tried once per scan.
- **Rate-limit bypass with spoofed client-IP headers** (#208). When the API4 burst was rate limited, the check stopped. It now sends a plain request, which must still be limited, then five requests that each carry a different `203.0.113.x` address in `X-Forwarded-For`, `X-Real-IP`, `X-Client-IP`, `True-Client-IP` and `X-Originating-IP`, then a second plain request. If at least four spoofed requests are accepted and both plain requests are still limited, MEDIUM "Rate Limiting Bypassed With Spoofed Client-IP Headers" is reported. A window that resets during the probe is not reported.

### Behaviour changes to know about

- A SQL error that the payload does not reproduce is reported as MEDIUM, not CRITICAL, and one that an ordinary value also triggers is reported as INFO. Confirming sends an ordinary value and the payload once more, only when a database error is seen.
- Fields not under test in the ReDoS and SQL/NoSQL checks are sent as `astf-filler` instead of `test`.
- The checks above send more requests than in 2.0.2 when their stricter request is rejected, and ambiguous auth paths get both kinds of check.
- Findings that could only be reached with the scan's credentials, headers or cookies now say so in the title and are rated lower.
- A database error caused by the target's own state is reported as INFO, not as an injection, even if it repeats.
- The credentialed mTLS comparison needs a server certificate the JVM trusts (add its authority to the Java trust store); against a self-signed certificate it reports INFO instead of comparing.
- A spec URL on another host is fetched without credentials, so one that requires them is not read unless the host is listed in `scopeHosts`.
- Without `--allow-destructive`, VAmPI's cross-user password change (`PUT /users/v1/{username}/password`) is reported as INFO "Check Held Back" instead of CRITICAL, because the password change is not sent. Add `--allow-destructive` to reproduce the account takeover against test accounts.
- A cross-user 2xx whose body does not contain the primary identity's object is MEDIUM instead of CRITICAL, and an object that is also returned without credentials is no longer reported as BOLA (ASTF-API2-2023 reports the missing authentication).
- Mass-assignment probes send a complete body on `POST`, so on a register-style endpoint they create accounts named `astf-<random>`, possibly as administrators if the endpoint is vulnerable. Remove them after a scan.
- Debug, actuator and API-documentation probes now run once per scan target even when `/` is not in the endpoint list, so grey-box scans send those extra requests. The `Cache-Control` check sends one extra request without credentials for each authenticated endpoint.
- A sensitive flow whose attempts were all rejected is reported as INFO or MEDIUM instead of HIGH. Open redirects and template injection, which could never be reported before, can now appear.
- The new bypass probes send extra requests: three more CORS probes per endpoint whose first origin is neither wildcarded nor reflected, roughly a dozen more anonymous requests per admin path that answers 401 or 403 (once per scan), and seven more requests on an API4 endpoint that rate limited the burst. A scan against a rate-limited target can therefore take slightly longer.

### Known limitations

- On a target that resets its own data while it is scanned (VAmPI's `GET /createdb` is tested by every check), the NoSQL bypass check can still occasionally report a CRITICAL "Authorization/Logic Bypass" on a field the endpoint ignores, when the invalid-value baseline and the payload each land on a different side of a reset. This was seen in 1 of 3 scans of VAmPI with ReDoS excluded. Re-run the scan, or check the finding by hand, before acting on a NoSQL bypass on such a target.
- **API6 skipped login and password-reset flows** (#175, part 2). `TESTING_GUIDELINES.md` says `ASTF-API6-2023` covers login, OTP, payment and password-reset flows, but the sensitive-flow path list had no `login`, `signin`, `password`, `reset` or `forgot`, so those endpoints were never exercised. They are now. The existing words are unchanged and match as before, so no endpoint that was tested before stops being tested. This change is meant to land after the fix for the first half of #175 (all-rejected attempts reported as HIGH), because a login that answers `{}` with a validation error would otherwise be reported at HIGH.

## 2.0.2 (patch)

A correctness release. No new command-line flags, no report-format changes, and exit codes keep their meaning. Every code fix below has unit tests, and the release build was checked with full scans of VAmPI, crAPI, DVGA and gRPC Goat in Docker, compared with the previous code (results are in the release pull request).

### Fixed

- **NoSQL bypass false positives** (#142, #147). The generalized bypass check from #136 reported CRITICAL bypasses on VAmPI, which has no NoSQL backend: a target that degraded mid-scan, or a create endpoint that succeeds once and then says "already exists", looked like a bypass. Failure responses are now recognized from parsed JSON, the baseline is re-checked before reporting, and a bypass is CRITICAL only if the same payload succeeds again; otherwise it is reported as MEDIUM "Possible Bypass (not reproducible)". If the target's answer to the invalid baseline changed during the scan, or the baseline got a server error instead of a rejection, the result is reported as INFO "Inconclusive" instead of being dropped.
- **GraphQL** (#140). The GraphQL suite ran once per scanned endpoint and repeated every finding; it now runs once per GraphQL URL. The circular-fragment probe, which crashes DVGA, now runs last and records whether the target recovered, so the checks after it no longer run against a dead server; the wait for recovery is bounded in time. Database errors leaked by resolvers (for example `sqlite3.OperationalError` with the SQL text) are now detected.
- **Soft-404 detection hid real endpoints** (#149). Short bodies and small insertions were treated as the catch-all page; very short bodies now have to match exactly.
- **Basic Auth** (#150). The authenticator replaced explicit `Authorization` headers, retried without limit and could send credentials to another host after a redirect. It now keeps explicit headers, retries once, and only for the target host.
- **SSRF false CRITICAL** (#151). An API that echoed the probe URL matched the probe's own indicator. Payload echoes are now removed before matching, a response identical to the baseline is ignored, and the endpoint's normal response is checked again before reporting, so content that changes during the scan (for example posts created by other checks) is not mistaken for fetched metadata. The evidence names the indicator that matched. A match in a non-2xx response is reported as MEDIUM "Possible Server Side Request Forgery" instead of CRITICAL.
- **ReDoS false HIGH** (#152). Any network error, including the scan's own timeout, was reported as a regex hang. Only a timeout right after a healthy baseline counts now.
- **Cookie store race** (#153). The cookie store was not thread-safe under the scanner's virtual threads.
- **Progress line** (#154). Tasks abandoned at the timeout were counted as completed, so an unfinished scan showed 100%. They are now reported separately.
- **Reports** (#155). Report files are written readable by the owner only, and a report path that is a symlink is replaced instead of written through. Session cookie values in cookie findings and token-like parameters in redirect `Location` evidence are masked.
- **Documentation.** The example configuration files used keys the loader does not read; they are rewritten and say that credentials come from command-line flags. The README CI example failed on any finding and passed silently on a scan error; it is fixed and pins the release. Build-from-source steps explain the JDK 21 requirement and the "class ASTFCli not found" error (discussion #46). Stale test counts are removed.

### Also new since 2.0.1

These were merged to main after the 2.0.1 release and ship for the first time in 2.0.2: behavioural SQL injection detection (#124), JWT none-algorithm check with the token's real claims (#126), unauthenticated probes no longer carrying credentials (#130), dependency security updates for jackson-databind and log4j (#131, #138), soft-404 screening of guessed paths (#134), NoSQL bypass detection beyond login fields (#136) and request bodies in configuration endpoints (#137).

### Behaviour changes to know about

- Report files are now `rw-------` on filesystems that support it.
- An SSRF indicator in a non-2xx response is reported as MEDIUM "Possible", not CRITICAL.
- A NoSQL bypass that does not reproduce is reported as MEDIUM, not CRITICAL, and a result taken while the target's behaviour changed is reported as INFO. Confirming a bypass sends the payload once more, only when a bypass is about to be reported.
- The progress line can now show fewer than 100% completed when a scan hits its timeout.

### Known limitations

- Some findings depend on the target's state during the scan. On VAmPI, other checks can delete the user `name1` before the SQL injection check reaches `DELETE /users/v1/name1`, so that finding occasionally does not appear; this happens with 2.0.1 as well.
- A target that cannot be reached is not reported as a scan error: the scan exits 1 with the generic fallback findings. Check the log for connection errors.
- On slow targets such as crAPI, ReDoS findings can still appear on a different endpoint from one run to the next.
- Planned for 2.1.0, not in this release: unauthenticated probes that still carry the scan's credentials in some checks, credentials sent to another host on redirects or to a spec URL named by Swagger UI, and auth-path detection that matches substrings.
