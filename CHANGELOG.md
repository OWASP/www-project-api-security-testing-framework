# Changelog

Releases before 2.0.2 are described on the [GitHub Releases page](https://github.com/OWASP/www-project-api-security-testing-framework/releases).

## 2.1.0 (unreleased)

### Fixed

- **Checks no longer disappear on look-alike paths.** Auth and 2FA endpoints were recognized by substring, so `/api/tokens`, `/api/authors`, `/api/authorities`, `/api/discount-codes` or `/api/otpauth-free-paths` were taken for login or OTP endpoints and never got the missing-auth and JWT checks. Path segments are now also split into words (on `-`, `_`, `.`, camelCase and acronym runs, so `OTPVerify` is `otp` + `verify` and `APIToken` is `api` + `token`, case-insensitively; keywords are also tried with letters and digits split apart, as in `oauth2token`; path parameters and the query string are ignored) and matched several ways. Strong stems match anywhere inside a word: `login`, `logon`, `signin`, `signon`, `authenticat`, `oauth`, `saml`, `jwt`, `accesstoken`, `authtoken`, `reauth`, `session` and `2fa`; `sso` counts only at the start of a word, and a few ordinary words that contain a stem (`possession`, `obsession`, `blogin`, `cataloging`, `designing`) are not counted. Weak keywords must be a whole word: `auth`, `authn`, `authorize`, `token`, `sign-in`, `sign-on`, `log-in`, `log-on` for login, and `mfa`, `otp`, `totp`, `two-factor`, `multifactor`, `verify`, `code` for 2FA. `authorization` counts only as a whole segment (`/api/authorization`, not `/api/authorization-rules`), and a word ending in `token` (`/api/gettoken`, `/api/refreshtoken`, `/api/idtoken`) or, for 2FA, in `otp` (`/api/sendotp`, `/api/verifyotp`) counts too. The 2.0.2 substring classification is still computed alongside, and checks are never taken away: a path gets the login checks if either classification calls it a login path, the 2FA checks if either calls it a 2FA path, and the missing-auth and JWT checks unless both call it a login or 2FA path. So where the two disagree (for example `/api/tokens`, `/api/authors` and `/api/discount-codes`, which 2.0.2 sent only login or OTP probes, or `/api/logon` and `/api/jwt`, which 2.0.2 sent only the generic checks), the path now gets both kinds of check. The NoSQL check treats a path as login-like (anonymous-first "Authentication Bypass" probes, retried with the configured credentials) when either the word classification or its 2.0.2 list (`login`, `auth`, `signin`, `session`) says so; where those two disagree and the anonymous probes showed no bypass, the probes are also sent the way 2.0.2 sent them, with 2.0.2's title, even when the scan has no configured credentials.
- **OpenAPI root-level security.** Discovery only read an operation's own `security`, so a spec that declares security at the root made every endpoint look public and the auth checks that need a protected endpoint skipped them. The effective requirement is now the operation's `security` (an explicit `[]` means public), else the root `security`, else "requires auth" when the spec defines `securitySchemes`. Swagger 2.0 specs are unchanged (all operations are still treated as protected).
- **Credentials stay on the target.** A redirect to another host carried the API-key header, custom headers and cookies with it (cookies are stored per host name, so another port on the same host got them too), and discovery fetched a spec URL named by a Swagger UI page with the scan's credentials even when it was on another host. Every request to a host:port other than the target is now sent without `Authorization`, the API-key header, `Proxy-Authorization` (kept only on a plain-http request sent through an HTTP proxy, which reads it itself; through an HTTPS tunnel the proxy credential goes on the CONNECT request), cookies, and every user-configured custom header except `Accept`, `Accept-Encoding`, `Accept-Language`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `User-Agent`, `Host` and `Connection`. The request itself is still made, but this does change discovery for a spec hosted on another host: it is fetched without credentials, so a spec that requires them is no longer read and its endpoints are not found unless that host is added to `scopeHosts`. A warning is logged the first time credentials are stripped for each host:port. A redirect from `http://host` to `https://host` on the target's own host (port 80 to 443) counts as the target and keeps every credential; other port changes do not. On a redirect chain that passes through a `scopeHosts` entry and returns to the target, the caller's `Authorization` is put back on every hop (OkHttp drops it whenever the scheme, host or port changes); a request sent without credentials stays without them. The new `scopeHosts` config key lists extra hosts (`host` or `host:port`) that may receive credentials.
- **`followRedirects` takes effect.** The setting existed but the client always followed redirects. It is now read from config files (`followRedirects: false`) and applied; the default stays `true`.
- **Unauthenticated means unauthenticated.** Several checks reported "without authorization", "publicly accessible" or anonymous-attacker results from requests that carried the scan's token, API key, custom credential headers and cookies. The BFLA admin-path and HTTP method probes, the debug/diagnostic endpoint probe, the shadow-endpoint and API documentation probes, the GraphQL IDE probe, the brute-force lockout and user enumeration checks, and the NoSQL bypass probes on login-like endpoints now send their requests with no credentials at all (every user-configured custom header is left off too, since identity often travels in headers such as `X-User-Id`, `X-Hasura-Role`, `X-Forwarded-User`, `X-Remote-User` or `X-Account-Id`; only `Accept`, `Content-Type`, `User-Agent`, `Accept-Language` and `Accept-Encoding` are still sent). When a resource only answers with the scan's credentials it is still reported, with "(reachable with the configured credentials)" in the title and a lower severity (for example an admin path drops from CRITICAL to MEDIUM, a NoSQL authentication bypass from CRITICAL to HIGH). The credentialed retry is only sent when the anonymous request was not accepted and the scan was configured with credentials (a token, API key, Basic Auth, or a custom header other than the protocol headers above); a cookie the target set during a scan with no credentials does not count. The mTLS comparison now presents the client certificate as its only credential, and the cross-user BOLA check sends the secondary identity's request with only the `--secondary-token` (no primary API key, custom headers other than the protocol headers above, or cookies).
- **Cross-user BOLA behind API gateways.** Since the secondary identity's request became the `--secondary-token` alone, a gateway that requires an application API key in addition to each user's bearer token rejected every secondary request with 401/403 and the cross-user check found nothing. When the secondary-token-only request gets 401 or 403 (and the primary request succeeded) and the scan has an application credential, the request is sent again with the secondary token plus that credential: the configured `--api-key` under its header, and any custom header whose name looks like an application or gateway key (contains `api-key`, `apikey`, `subscription-key`, `app-key`, `app-id`, `application-key`, `application-id`, `client-id`, `client-key`, `gateway-key` or `consumer-key`, ignoring case, `-` and `_`, and not `user`, `account`, `session`, `role`, `member`, `customer` or `token`). It never carries the primary bearer token, cookies or other custom headers. A control request with the application credential alone (no bearer token) is also sent. If it is rejected, "Broken Object Level Authorization (Cross-User Access Confirmed, secondary token with the application API key)" is reported at CRITICAL; if the control could not be sent, at HIGH; if the application credential alone is accepted too, "Broken Object Level Authorization (Cross-User Access, application API key alone also accepted)" is reported at MEDIUM. The evidence gives the status for the primary request, the secondary token alone, the secondary token with the application credential and the control, and names the application credential headers (not their values). A plain bearer API, or a gateway that accepts the secondary token alone, is tested exactly as before and no API key is sent on its secondary request.
- **Login walls are not exposed endpoints.** The debug/diagnostic and BFLA admin-path probes are sent without credentials, but their soft-404 screening compared the answer with what an unknown path returns *with* credentials. Behind a login wall that answers every anonymous request with the same sign-in page, each probed path was reported (up to 30 "Debug/Diagnostic Endpoint Exposed" and 21 CRITICAL admin findings). An anonymous probe is now compared with an unknown-path baseline that is also fetched without credentials (cached separately); a credentialed retry is still compared with the credentialed baseline. The documentation probe already compared each answer with a fallback page fetched the same way, and the shadow-endpoint probe does not use a soft-404 baseline.
- **Lockout check behind a gateway.** The brute-force lockout attempts are sent without credentials. When every attempt got the same 401/403 as a request to a path that does not exist, the attempts were rejected before reaching the login handler, yet "No Account Lockout" was reported. Now, if the scan has credentials, the attempts are repeated with them and a result is reported as "(reachable with the configured credentials)" at LOW; the evidence says which way the attempts were sent. Without credentials nothing is reported about lockout in that case. A login handler that itself answers a wrong password with 401 (so a path that does not exist gets a different answer) is still reported as before.
- **mTLS comparison on APIs that also need a token.** Since the client certificate became the only credential on the mTLS requests, an API that needs both a certificate and a bearer token or API key rejected the valid certificate, and the arbitrary-certificate comparison stopped there. The certificate-only pair is still sent first and reported as before. When the valid certificate alone is not accepted and the scan has credentials, the valid and the untrusted certificate are both sent again with the same configured credentials (no cookies, so the two requests differ only in the certificate). If both are accepted, "Arbitrary Client Certificate Accepted (mTLS, with the configured credentials)" is reported at HIGH, and the evidence gives the certificate-only status and says the comparison was made with the configured credentials.

## 2.0.2 (patch)

A correctness release. No new command-line flags, no report-format changes, and exit codes keep their meaning. Every code fix below has unit tests, and the release build was checked with full scans of VAmPI, crAPI, DVGA and gRPC Goat in Docker, compared with the previous code (results are in the release pull request).

### Fixed

- **NoSQL bypass false positives** (#142, #147). The generalized bypass check from #136 reported CRITICAL bypasses on VAmPI, which has no NoSQL backend: a target that degraded mid-scan, or a create endpoint that succeeds once and then says "already exists", looked like a bypass. Failure responses are now recognized from parsed JSON, the baseline is re-checked before reporting, and a bypass is CRITICAL only if the same payload succeeds again; otherwise it is reported as MEDIUM "Possible Bypass (not reproducible)". If the target's answer to the invalid baseline changed during the scan, or the baseline got a server error instead of a rejection, the result is reported as INFO "Inconclusive" instead of being dropped.
- **GraphQL** (#140). The GraphQL suite ran once per scanned endpoint and repeated every finding; it now runs once per GraphQL URL. The circular-fragment probe, which crashes DVGA, now runs last and records whether the target recovered, so the checks after it no longer run against a dead server; the wait for recovery is bounded in time. Database errors leaked by resolvers (for example `sqlite3.OperationalError` with the SQL text) are now detected.
- **Soft-404 detection hid real endpoints** (#149). Short bodies and small insertions were treated as the catch-all page; very short bodies now have to match exactly.
- **Basic Auth** (#150). The authenticator replaced explicit `Authorization` headers, retried without limit and could send credentials to another host after a redirect. It now keeps explicit headers, retries once, and only for the target host.
- **SSRF false CRITICAL** (#151). An API that echoed the probe URL matched the probe's own indicator. Payload echoes are now removed before matching, a response identical to the baseline is ignored, and the endpoint's normal response is checked again before reporting, so content that changes during the scan (for example posts created by other checks) is not mistaken for fetched metadata. The evidence names the indicator that matched. A match in a non-2xx response is reported as MEDIUM "Possible Server Side Request Forgery" instead of CRITICAL.
- **ReDoS false HIGH** (#152). Any network error, including the scan's own timeout, was reported as a regex hang. Only a timeout right after a healthy baseline counts now.
- **Cookie store race** (#153). The cookie store was not thread-safe under the scanner's virtual threads.
- **Progress line** (#154). Tasks abandoned at the timeout were counted as completed, so an unfinished scan showed 100%. They are now reported separately.
- **Reports** (#155). Report files are written readable by the owner only, and a report path that is a symlink is replaced instead of written through. Session cookie values in cookie findings and token-like parameters in redirect `Location` evidence are masked.
- **Documentation.** The example configuration files used keys the loader does not read; they are rewritten and say that credentials come from command-line flags. The README CI example failed on any finding and passed silently on a scan error; it is fixed and pins the release. Build-from-source steps explain the JDK 21 requirement and the "class ASTFCli not found" error (discussion #46). Stale test counts are removed.

### Also new since 2.0.1

These were merged to main after the 2.0.1 release and ship for the first time in 2.0.2: behavioural SQL injection detection (#124), JWT none-algorithm check with the token's real claims (#126), unauthenticated probes no longer carrying credentials (#130), dependency security updates for jackson-databind and log4j (#131, #138), soft-404 screening of guessed paths (#134), NoSQL bypass detection beyond login fields (#136) and request bodies in configuration endpoints (#137).

### Behaviour changes to know about

- Report files are now `rw-------` on filesystems that support it.
- An SSRF indicator in a non-2xx response is reported as MEDIUM "Possible", not CRITICAL.
- A NoSQL bypass that does not reproduce is reported as MEDIUM, not CRITICAL, and a result taken while the target's behaviour changed is reported as INFO. Confirming a bypass sends the payload once more, only when a bypass is about to be reported.
- The progress line can now show fewer than 100% completed when a scan hits its timeout.

### Known limitations

- Some findings depend on the target's state during the scan. On VAmPI, other checks can delete the user `name1` before the SQL injection check reaches `DELETE /users/v1/name1`, so that finding occasionally does not appear; this happens with 2.0.1 as well.
- A target that cannot be reached is not reported as a scan error: the scan exits 1 with the generic fallback findings. Check the log for connection errors.
- On slow targets such as crAPI, ReDoS findings can still appear on a different endpoint from one run to the next.
- Planned for 2.1.0, not in this release: unauthenticated probes that still carry the scan's credentials in some checks, credentials sent to another host on redirects or to a spec URL named by Swagger UI, and auth-path detection that matches substrings.
