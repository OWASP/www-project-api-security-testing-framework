# Changelog

Releases before 2.0.2 are described on the [GitHub Releases page](https://github.com/OWASP/www-project-api-security-testing-framework/releases).

## 2.1.0 (unreleased)

Several checks claimed to be unauthenticated or to use one identity while sending the scan's credentials, and credentials could follow a redirect to another host. This release sends the stricter request first (no credentials, the secondary token alone, only the target host). When that request is rejected, the check falls back to the request 2.0.2 sent, so it still finds what 2.0.2 found. A result that cannot be shown to be unauthenticated or attributable to one identity is reported at a lower severity, and its title and evidence say what was sent.

### Fixed

- **Checks no longer disappear on look-alike paths.** Auth and 2FA endpoints were recognized by substring, so `/api/tokens`, `/api/authors`, `/api/authorities`, `/api/discount-codes` and `/api/otpauth-free-paths` were taken for login or OTP endpoints and never got the missing-auth and JWT checks. Paths are now also split into words (on `-`, `_`, `.`, camelCase and acronym runs, case-insensitively, ignoring path parameters and the query string) and matched by stems (`login`, `logon`, `signin`, `authenticat`, `oauth`, `saml`, `jwt`, `session`, and others) and whole-word keywords (`auth`, `token`, `otp`, `mfa`, and others). The 2.0.2 substring classification is still computed alongside and nothing is taken away: a path gets the login checks if either classification calls it a login path, the 2FA checks if either calls it a 2FA path, and the missing-auth and JWT checks unless both do. Where the two disagree (`/api/tokens`, `/api/logon`, `/api/jwt`, and others) the path now gets both kinds of check. The NoSQL check uses the same rule for "login-like". Ambiguous paths receive more requests.
- **OpenAPI root-level security.** Discovery only read an operation's own `security`, so a spec with root-level security made every endpoint look public. The effective requirement is the operation's `security` (an explicit `[]` means public), else the root `security`, else "requires auth" when the spec defines `securitySchemes`. Swagger 2.0 specs are unchanged.
- **Credentials stay on the target.** A redirect to another host carried the API-key header, custom headers and cookies with it, and discovery fetched a spec URL named by a Swagger UI page with the scan's credentials even when it was on another host. A request to any host:port other than the target is still made, but without `Authorization`, the API-key header, cookies, `Proxy-Authorization` (kept only on a plain-http request through an HTTP proxy) and every configured custom header except `Accept`, `Accept-Encoding`, `Accept-Language`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `User-Agent`, `Host` and `Connection`. A warning is logged once per host:port. `http://host` redirecting to `https://host` on the target's own host (port 80 to 443) counts as the target; other port changes do not. A redirect from https to plain http never carries credentials, even to a host listed in the new `scopeHosts` config key (`host` or `host:port`), which lists extra hosts that may receive them. On a redirect chain through a listed host and back to the target, `Authorization` is restored on every in-scope hop. `followRedirects` now takes effect (default `true`).
- **Unauthenticated means unauthenticated.** The BFLA admin-path and HTTP-method probes, the debug, shadow-endpoint, documentation and GraphQL IDE probes, the missing-authentication check, the brute-force lockout and user-enumeration checks and the NoSQL bypass probes on login-like paths reported "without authorization", "publicly accessible" or anonymous-attacker results from requests that carried the token, API key, custom headers and cookies. They now send the request with no credentials and no custom header except the protocol headers above (identity often travels in headers such as `X-User-Id`). If that request is not accepted, the request 2.0.2 sent is sent too, and a result is reported as "(reachable with the configured credentials)", "(reachable with the configured headers)" or "(reachable with cookies set during the scan)" at a lower severity (an admin path drops from CRITICAL to MEDIUM, a NoSQL authentication bypass from CRITICAL to HIGH). The missing-authentication check, when rejected without any custom header, is also sent with no `Authorization`, API key or cookie but with the custom headers kept (the 2.0.2 request) and, if accepted, reported with the kept header names in its evidence. The GraphQL guessed-cookie comparison is sent without credentials when the baseline it compares with was anonymous.
- **Cross-user BOLA behind API gateways.** The secondary identity's request now carries only `--secondary-token`, with no primary API key, custom headers or cookies. A gateway that also requires an application key rejected that request, so the secondary token is then sent plus the application credential (the `--api-key` and any custom header whose name looks like an application or gateway key), with a control request sending that credential alone to grade the result: CRITICAL, HIGH if the control could not be sent, or MEDIUM if the application credential alone reaches the object. If both are rejected, the request 2.0.2 sent (the primary request with only `Authorization` replaced) is sent and, if accepted, reported as "Broken Object Level Authorization (Cross-User Access, other configured headers kept)" at HIGH, listing the headers that rode along. A plain bearer API is tested as before and no API key is sent.
- **Login walls are not exposed endpoints.** The debug and BFLA admin probes were sent without credentials but screened against an unknown-path baseline fetched with credentials, so behind a login wall every probed path was reported. An anonymous probe is now compared with an unknown-path baseline that is also fetched without credentials.
- **Lockout check behind a gateway.** When every attempt got the same 401/403 as a path that does not exist, the attempts may not have reached the login handler, yet "No Account Lockout" was reported at MEDIUM. The attempts are now repeated with the configured credentials when there are any, and a result that still cannot be told apart from a pre-handler rejection is reported at LOW as "No Account Lockout or Rate Limiting on Repeated Failed Logins (not confirmed)", saying so. It is never dropped.
- **mTLS comparison on APIs that also need a token.** The certificate-only pair is sent first, as before. If the valid certificate alone is rejected and the scan has credentials, both certificates are sent again with the same configured credentials, over a connection that validates the server's certificate and host name (a token is never sent over an unvalidated connection). If the server's certificate is not trusted by this JVM, no credential is sent and an INFO finding "mTLS Certificate Comparison With Credentials Not Made (server certificate not trusted)" says so.

### Behaviour changes to know about

- The checks above send more requests than in 2.0.2 when their stricter request is rejected, and ambiguous auth paths get both kinds of check.
- Findings that could only be reached with the scan's credentials, headers or cookies now say so in the title and are rated lower.
- The credentialed mTLS comparison needs a server certificate the JVM trusts (add its authority to the Java trust store); against a self-signed certificate it reports INFO instead of comparing.
- A spec URL on another host is fetched without credentials, so one that requires them is not read unless the host is listed in `scopeHosts`.

## 2.0.2 (patch)

A correctness release. No new command-line flags, no report-format changes, and exit codes keep their meaning. Every code fix below has unit tests, and the release build was checked with full scans of VAmPI, crAPI, DVGA and gRPC Goat in Docker, compared with the previous code (results are in the release pull request).

### Fixed

- **NoSQL bypass false positives** (#142, #147). The generalized bypass check from #136 reported CRITICAL bypasses on VAmPI, which has no NoSQL backend: a target that degraded mid-scan, or a create endpoint that succeeds once and then says "already exists", looked like a bypass. Failure responses are now recognized from parsed JSON, the baseline is re-checked before reporting, and a bypass is CRITICAL only if the same payload succeeds again; otherwise it is reported as MEDIUM "Possible Bypass (not reproducible)". If the target's answer to the invalid baseline changed during the scan, or the baseline got a server error instead of a rejection, the result is reported as INFO "Inconclusive" instead of being dropped.
- **GraphQL** (#140). The GraphQL suite ran once per scanned endpoint and repeated every finding; it now runs once per GraphQL URL. The circular-fragment probe, which crashes DVGA, now runs last and records whether the target recovered, so the checks after it no longer run against a dead server; the wait for recovery is bounded in time. Database errors leaked by resolvers (for example `sqlite3.OperationalError` with the SQL text) are now detected.
- **Soft-404 detection hid real endpoints** (#149). Short bodies and small insertions were treated as the catch-all page; very short bodies now have to match exactly.
- **Basic Auth** (#150). The authenticator replaced explicit `Authorization` headers, retried without limit and could send credentials to another host after a redirect. It now keeps explicit headers, retries once, and only for the target host.
- **SSRF false CRITICAL** (#151). An API that echoed the probe URL matched the probe's own indicator. Payload echoes are now removed before matching, a response identical to the baseline is ignored, and the endpoint's normal response is checked again before reporting, so content that changes during the scan (for example posts created by other checks) is not mistaken for fetched metadata. The evidence names the indicator that matched. A match in a non-2xx response is reported as MEDIUM "Possible Server Side Request Forgery" instead of CRITICAL.
- **ReDoS false HIGH** (#152). Any network error, including the scan's own timeout, was reported as a regex hang. Only a timeout right after a healthy baseline counts now.
- **Cookie store race** (#153). The cookie store was not thread-safe under the scanner's virtual threads.
- **Progress line** (#154). Tasks abandoned at the timeout were counted as completed, so an unfinished scan showed 100%. They are now reported separately.
- **Reports** (#155). Report files are written readable by the owner only, and a report path that is a symlink is replaced instead of written through. Session cookie values in cookie findings and token-like parameters in redirect `Location` evidence are masked.
- **Documentation.** The example configuration files used keys the loader does not read; they are rewritten and say that credentials come from command-line flags. The README CI example failed on any finding and passed silently on a scan error; it is fixed and pins the release. Build-from-source steps explain the JDK 21 requirement and the "class ASTFCli not found" error (discussion #46). Stale test counts are removed.

### Also new since 2.0.1

These were merged to main after the 2.0.1 release and ship for the first time in 2.0.2: behavioural SQL injection detection (#124), JWT none-algorithm check with the token's real claims (#126), unauthenticated probes no longer carrying credentials (#130), dependency security updates for jackson-databind and log4j (#131, #138), soft-404 screening of guessed paths (#134), NoSQL bypass detection beyond login fields (#136) and request bodies in configuration endpoints (#137).

### Behaviour changes to know about

- Report files are now `rw-------` on filesystems that support it.
- An SSRF indicator in a non-2xx response is reported as MEDIUM "Possible", not CRITICAL.
- A NoSQL bypass that does not reproduce is reported as MEDIUM, not CRITICAL, and a result taken while the target's behaviour changed is reported as INFO. Confirming a bypass sends the payload once more, only when a bypass is about to be reported.
- The progress line can now show fewer than 100% completed when a scan hits its timeout.

### Known limitations

- Some findings depend on the target's state during the scan. On VAmPI, other checks can delete the user `name1` before the SQL injection check reaches `DELETE /users/v1/name1`, so that finding occasionally does not appear; this happens with 2.0.1 as well.
- A target that cannot be reached is not reported as a scan error: the scan exits 1 with the generic fallback findings. Check the log for connection errors.
- On slow targets such as crAPI, ReDoS findings can still appear on a different endpoint from one run to the next.
- Planned for 2.1.0, not in this release: unauthenticated probes that still carry the scan's credentials in some checks, credentials sent to another host on redirects or to a spec URL named by Swagger UI, and auth-path detection that matches substrings.
